# Prompt to continue the mobile app in a fresh session

Paste everything inside the block into a new Claude Code session opened in `/home/sedky02/my-pc/professional-projects/MoFin`. It authorizes **local commits only** (never a push) and tells the agent to keep working until the session ends.

````text
You are continuing the MoFin mobile app (Expo, iOS + Android) in /home/sedky02/my-pc/professional-projects/MoFin. Work autonomously until the session ends. I authorize LOCAL git commits for this work; you must never push.

READ FIRST (in this order)
1. docs/mobile/README.md        decisions, architecture, rules for every phase
2. docs/mobile/PROGRESS.md      status, decisions log, last handoff
3. the brief of the first unfinished phase: docs/mobile/phase-N-*.md
4. frontend/mobile/README.md and frontend/mobile/AGENTS.md (Expo's own guidance: use versioned Expo docs, `npx expo install`, never hand-edit ios/ or android/)
5. backend/CLAUDE.md before touching the backend

HOW TO WORK
1. Run `git status`. If earlier work is uncommitted (docs/mobile, frontend/mobile), commit it first in logical groups.
2. Build a task list from the remaining phases in PROGRESS.md (first unfinished phase onward; one task per step group of its brief). Keep it updated as you go.
3. Do the tasks in order. After EACH task:
   a. Run the checks: in frontend/mobile `npm run typecheck && npm run lint && npm test`; if the backend changed, in backend `npm test && npm run test:e2e && npm run lint`. For UI work, also check it in the browser through `npm run web` (Playwright screenshots at 390 and 820 px wide, light and dark). There is no phone or emulator here.
   b. If green, stage ONLY that task's files (never `git add -A`) and commit locally.
   c. Print the commit message and its short hash, then continue with the next task.
4. Commit messages: ONE line, conventional style `type(scope): message` with scope `mobile`, `api` or `docs`. No body, no trailers (no Co-Authored-By), no mention of AI or Claude, use the existing git identity, never pass --author.
5. Git limits: never push, never force, never amend/reset/rebase, no branches or worktrees. Don't commit `.env`, secrets, `.claude/` or `docs/demo-video/`. Don't edit `frontend/web` unless the phase brief says so.
6. At the end of each phase: tick it in docs/mobile/PROGRESS.md (status, decisions, what you could not verify) and commit that as `docs(mobile): ...`.

KEEP GOING; STOP ONLY FOR
- a step marked GATE in a brief (ask me first),
- a new BACKEND dependency or database schema change that a brief does not already approve (`jose` is approved; the Apple/appleId work is deferred and out of scope),
- a manual step only I can do (deploying the backend, EAS login, Google/Apple consoles, testing on a device): write it into the PROGRESS.md handoff, skip to the next task that is not blocked, and carry on,
- an error you cannot resolve after 2-3 genuine attempts: record it and move on.
Make routine decisions yourself, following the brief's defaults, and log them in PROGRESS.md.

QUALITY RULES
- Money, decimals and dates: use the copied src/core helpers; never reimplement formatting or arithmetic. The web app is the reference for behaviour and copy.
- Follow docs/mobile/README.md "Rules for every phase" and frontend/mobile/README.md conventions (routes only in src/app; Testing Library 14 is async; theme is generated by `npm run theme:sync`).
- Model routing: follow the MODEL ROUTING section below.
- Use the installed skills at the moments they fit (invoke them with the Skill tool; subagents get the same skills):
    react-native-design ........ screens, navigation, styling, Reanimated animations (phases 5-8)
    mobile-ios-design / mobile-android-design: platform conventions for headers, tabs, sheets, touch targets (phases 5-6, 8)
    react-native-best-practices / vercel-react-native-skills: lists (FlashList), re-renders, startup, bundle size, memory (phases 6, 8, 9)
    accessibility-compliance ... VoiceOver/TalkBack labels, contrast, focus order (phases 5, 8, 9)
    also tdd, diagnosing-bugs, simplify and ux-audit (on the web preview) when they fit, and the Expo plugin if it is installed.
  Always verify against the real Expo SDK 58 docs before using an Expo or React Native API you are unsure about; the skills are guidance, not documentation.

MODEL ROUTING (you cannot run /model yourself; use subagents to get the right model)
Subagent dispatch is explicitly allowed for this work (the paused backlog workflow's ban does not apply here).
Recommended model per task:
  - Phase 2 core copy ........ sonnet, effort medium; afterwards ONE read-only reviewer on opus, effort high, to check money/date/format parity of the diff and return findings
  - Phase 3 backend sign-in .. opus, effort high
  - Phase 4 API client + auth  opus, effort high
  - Phase 5 shell + UI kit ... sonnet, effort medium
  - Phase 6a accounts/categories, 6c dashboard + onboarding: sonnet, effort medium
  - Phase 6b transactions: the create/edit form (split lines, recurring, validation) on opus, effort high; list and detail on sonnet, effort medium
  - Phase 7 goals/drafts/settings: sonnet, effort medium; the delete-data, delete-account, password and sign-out-everywhere flows on opus, effort high
  - Phase 8 polish: sonnet, effort medium
  - Phase 9: tests on sonnet; the security review as a read-only reviewer on opus, effort high
  - purely mechanical work (strings, icon maps, test scaffolding): haiku, effort low
Rules:
  1. If you already run on the recommended model, do the task yourself. If not, and the task is bigger than a few files or ~50 lines, delegate it to ONE subagent through the Agent tool (subagent_type "general-purpose", `model` and `effort` as above). Don't delegate tiny edits just to change model.
  2. The subagent starts with no memory, so its prompt must be self-contained: paste the brief's step text and the README "Rules for every phase", name the exact files to read and write, state the acceptance criteria and the checks to run. Tell it: do NOT commit, do NOT push, do NOT edit docs/mobile/PROGRESS.md, touch only the files the task needs; finish with a report listing the files changed, each check and its result, decisions made, anything left undone, and any question for me.
  3. Subagents cannot ask me anything. Treat their questions as yours: decide with the brief's defaults, or record the item as blocked in PROGRESS.md.
  4. When a subagent returns, review `git diff`, re-run the checks yourself, fix small problems (or re-dispatch with precise feedback), then commit as usual. YOU own every commit and PROGRESS.md.
  5. Run subagents in parallel only for independent tasks that touch different files (for example 6a and 6c), at most 3 at once. Never run two on the same files.
  6. Keep your own context lean: summarize a subagent's report in a few lines; don't paste it back in full.

WHEN THE SESSION IS ENDING (or your context is nearly full)
Write a "Handoff" section in docs/mobile/PROGRESS.md: what is done, what is next, what is blocked, and the exact manual steps I must do. Commit it as `docs(mobile): ...`, then give me a short summary: the list of commits (hash + message) and anything I need to do.
````

## Model routing inside one session
A prompt cannot change the model of the session it runs in (`/model` is a command only you can run). The prompt above therefore makes the session an **orchestrator**: it does the work that matches its own model and hands the rest to subagents that run on the right model (Opus with effort high for auth, backend and money-critical code; Sonnet for the bulk of the screens; Haiku for mechanical edits).

- **Start the session on Sonnet 5.5** (`/model sonnet` before pasting). It stays cheap as the long-lived orchestrator, and Opus is used only where the routing table says so.
- If you start on Opus instead, the same rules send the Sonnet-recommended work to Sonnet subagents, which saves tokens.
- Cost: each subagent starts cold (it re-reads the brief and files), so small steps are done inline, and subagent reports are not shown to you; the orchestrator summarizes them and commits.
- Still want strict control per phase? Run the prompt in separate sessions and end it with "Work only on phase N this session".
